## Reproduction and observation

1. Installed the synthetic provider from its VSIX in a fresh extensions directory and launched a separate empty Code window.
2. Opened only `fixture.orqtest` with the custom editor. Trace: `document_open`, `editor_resolve`.
3. Edited, Undid, Redid; trace: `edit_received`, `undo`, `redo`, `dirty_edit_done`, `backup`.
4. Invoked `workbench.action.saveWorkspaceAs`, saved `probe.code-workspace`, and clicked the actual **Restart Anyway** button in VS Code's custom editor warning. Screenshot `after-workspace-save.png` captures the warning.
5. The original extension host process **3810** deactivated. A new host process **4043** activated and recorded `alive: { openDocuments: [], tabs: [{ label: "fixture.orqtest", dirty: true, active: true }] }`.
6. The surviving webview accepted a click: its button changed to **Clicked 1** in `after-webview-click.png`. There was no post-restart `webview_message_received` or `edit_received` callback in the new extension host.
7. The new host invoked VS Code Save. The command resolved, but the tab remained `dirty: true`, with no `save` callback in the trace. The command returning without an error therefore must not be treated as a successful save.

## Limits and next gate

The test uses a synthetic provider, Linux x64, and one version of VS Code. It did not force-close the window or demonstrate actual loss of data. The screenshot and event trace together support a stale custom editor connection and a save that did not complete in this setup. A fix requires a focused regression inside the VS Code codebase, a minimal implementation, the same test again, and independent upstream review. Preserve this First Red unchanged.
